# Contract sediment cleanup · 契约沉积清理

**沉积（sediment）**：活文档靠追加版本增量生长——每次修订不去改原文，而是在末尾叠一章"vN 变更"。死规则留在原地（"X 起已废除，见下章"），同一规则在不同时代被重复定义，同一主题碎在多个版本章节里。代价：读者必须先把死规则读进来再学着忘掉；矛盾处让行为变成掷硬币。

## 检测信号

- 章节按版本号组织（v3 / v4 / v10……）而不是按主题组织。
- 死规则路标："X 起已废除"、"不再生效"、"见下章"、"X 起改为"。
- 同一概念两处定义、取值不同（四档 vs 五档状态词；心跳 60s vs 90s vs 120s）。
- 同一主题的规则散在 3 处以上（如签批单规则分住 v4、v5、v12 三节）。
- "新纪律"小节成串（v11 纪律 / v12 纪律 / v13 纪律），且与别的文件内容重复。

## Procedure

1. **全量盘点规则**：通读全文，逐条列出规则及所在章节，每条标记 live / dead / superseded。
2. **以代码与现实裁决矛盾**，不是以文档新旧为准——文档可能几处都错。去源码里找常量与行为（例：心跳矛盾以 watcher 的 `LIAISON_ALIVE_FRESH_MS=90s` 为准，据此把 wait timeout 改成 60s）。代码也无法裁决的矛盾，问维护者，别猜——契约是权威文档，猜错比留着更糟。
3. **定主题骨架**：按 subject 排章节（铁律 → 格式 → 门禁 → 协议总表 → 台账 → 事件与心跳 → 运行状态），不按时间。每条 live 规则恰好有一个家。
4. **只写现行状态**：live 规则在其主题家写一次。dead 规则**删除**，不要保留原文再划线/标注"已废除"——negation 会把被禁行为拖回 context（版本说明一节除外，见第 6 条）。过渡句改写为平铺直述："v5 起改为两步确认制" → "现行：两步确认制——先提案，用户同意后成卡"。
5. **保留溯源标签**：紧凑的决策编号（MSG-xxx、ticket 号）内联保留——成本极低，换来考古能力。版本号标签（v3/v4…）随旧结构一起删除。
6. **末尾留一节「版本说明」**：一处写清当前状态对应的时间点、哪些历史规则已废除不再生效。维护者考古去那一节，正文零负担。
7. **重指 inbound pointers**：代码注释、其他文档里指向"第 N 行 / v11 ⑦"的引用，全部改为章节名。永不指行号——行号每次编辑都腐烂。
8. **验证**：自动断言——死规则关键词只剩「版本说明」一节；每个关键主题小节存在；同口径数值全文唯一（状态词列表只出现一次）；inbound pointer 的目标小节存在。

## 边界（别清过头）

- 沉积清理 = 删死的、并重的、聚散的，**不是**激进压缩。实现细节若查阅昂贵（584KB HTML 里的压缩阶梯参数），契约里留一段压缩摘要是对的，别删。
- 行为规则与协议规则分家时：协议住契约，行为住执行者指令，指令用一句话 pointer 指到契约小节——不要两边各写一份。

## 案例锚点
