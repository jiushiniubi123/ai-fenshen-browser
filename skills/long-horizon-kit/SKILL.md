# long-horizon-kit

## 什么时候用

- 用户要开始一个步骤较多的任务，担心中途跑偏、上下文被压缩后丢线索、提前收尾。
- 任务会跨多轮会话，或需要多次清空上下文才能做完。
- 用户明确要「长任务模板」「任务骨架」「防跑偏」。

不适用：一次能做完的小任务。

## 它解决两个问题

1. **状态在对话里会丢，在文件里不会。** 所以进度、待办、功能清单都落盘。
2. **模型会宣称自己做完了。** 所以「完成」由命令的退出码决定，不由模型自述。

## 怎么用

1. 在目标项目根目录建一个 `longtask-kit/` 目录（或按用户偏好直接放根目录）。
2. 把 `assets/` 下 7 个文件复制过去。
3. 让用户填三处，这三处填不出来就说明任务还没想清楚：
   - `features.json` 的 `features`：每条 = 一个功能 + 一句能判断真假的验收标准 + 一条 `check` 命令
   - `features.json` 的 `baseline_test`：一条跑得快的基础测试
   - `agent-rules.md`：粘进 agent 的系统提示或 `AGENTS.md`
4. 运行 `python warmup.py` 开始第一轮。

## 每轮循环

```
python warmup.py        看现在在哪、起点干不干净
写 todo.md              只写本轮这一个功能（覆盖，不追加）
做事
python verify.py F00N   通过 → passes 自动翻 true；没通过 → 保持 false
追加 progress.md        做了什么、证据、卡点。失败也要写
git commit
```

## 设计上的取舍

- `todo.md` 是**覆盖**，`progress.md` 是**追加**。前者描述本轮，后者是历史。
- `passes` 只允许 `verify.py` 翻转。手改一次，清单就不再是证据。
- 每个功能只配一条 check 命令。配不出来，说明验收标准还是模糊的——先让用户把它写清楚。
- 两个脚本只用标准库，跨平台，不引入依赖。

## 常见误用

- 功能粒度太粗（一个 `check` 要跑十几分钟）。粒度要小到「一轮能做完并验证」。
- 把 `todo.md` 当历史文件追加，越写越长，失去「本轮」的作用。
- 失败时不写 `progress.md`。删掉失败记录，下一轮还会犯同一个错。
